## Recommendation

Add a small, curated set of **mechanism figures**, with one canonical editable source per figure and a written contract for what it depicts. Reuse study-owned diagrams in the book as derived assets. Give book-only cross-study concepts their own sources. Do not produce one UML diagram per design or turn the six-family taxonomy into a single crowded wall chart.

Start with a proof set of four figures, in this order:

1. **Book information placement:** a compact ownership/maintenance map for derive, index, rollup, rolldown, embed, and external cache. Label it a conceptual illustration, not a measured comparison. This visualizes the decision path shared by `how-to-choose.typ` and `information-placement.typ`; place it once and refer to it elsewhere.
2. **Study 04 concurrency and derived state:** one short sequence with transaction boundaries and acknowledgement, contrasting version-checked retry with lock-before-update, plus a separate small panel for atomic rollup publication versus the `x2` after-commit negative control. This belongs in Study 04 first; the book's concurrency/derived-state concepts can reuse the relevant panel. Do not merge distinct designs into a single timeline that implies they ran together.
3. **Study 05 cache race:** writer, database, cache, two application instances, and an old fill. Show commit, acknowledgement, invalidate/fence, and the stale publication that must be rejected. Mark the relaxed failure branch and strict contract separately. This addresses a mechanism that prose alone makes easy to reverse in time.
4. **Study 02/03 answerability over time:** reuse or adapt the Study 03 expiry sequence, and add only the minimal Study 02 sale/refund/ledger timeline needed to show why a current ticket row cannot answer a refund-history question. An existing schema diagram should be reused, not redrawn, if it already shows the entities accurately.

Each figure should have a short caption containing: `kind` (logical model, implemented flow, negative control, or measured observation), applicable design IDs and source commit/tag, owning `.puml` path, the invariant or question it explains, and a link to the relevant v2 claim card when discussing a measured result. Keep throughput, ratios, and causal performance claims in prose and registry cards beside the figure, not baked into SVG text. An unmeasured arrow is an illustration of a design contract; it is not evidence that the race or speed was observed.

## Reasoning and trade-offs

The most valuable pictures explain **where the fact lives**, **who gets to change it**, and **which event happens before acknowledgement**. Entity UML is strong for the first; sequence or state diagrams are stronger for the latter two. The book already explains these axes in prose, and Studies 01–03 already supply most of the entity views. Adding more copies of those schemas would increase maintenance without resolving the reader's hardest timing questions.

For reproducibility, pin PlantUML to an immutable image digest in the repository's image-version scheme and render only inside Podman. Check in SVG with its `.puml`, and use a deterministic export step to place study-derived SVGs under `book/assets/` because today's `book/build.sh` exposes only `book/` to Typst. Record for each exported asset its canonical source path and hash, renderer digest, output hash, and applicable revision. Extend the book source/build digest to include figure sources and embedded SVG bytes; reject stale exports. Keep just one editable source even when the built book necessarily carries a copy of the SVG. The book's existing palette, direct/analogy/gap labels, and A4 text scale should govern captions and styling; render and inspect the actual PDF for legibility, wrapping, grayscale distinction, and readable text size.

The figure contract needs a manual SQL/harness review at the named revision. Automation can prove that an SVG came from its source and that cited claim IDs exist; it cannot prove a sequence's transaction boundary or a claim about a plan. The D3 heap-fetch contradiction is a concrete reason to audit existing diagrams before importing them. A visual that is easy to understand but too absolute is worse than careful prose.

This approach costs a small manifest/export tool and review time. It intentionally limits illustration count. Book page count can grow only when a figure earns space by making a decision or failure mode clearer than nearby text.

## Alternatives

- **Draw everything directly in Typst or switch to Mermaid.** This could simplify one build, but it creates a second diagram language and abandons the existing PlantUML corpus. Reconsider if a two-figure Podman/Typst pilot proves PlantUML SVGs unreadable or unmaintainable.
- **Auto-generate all diagrams from SQL.** Useful as a schema-drift check, but SQL alone cannot express lease expiry, client acknowledgement, retry bounds, or who owns a cache fence. It cannot replace reviewed sequence sources.
- **Reuse every existing study diagram verbatim.** Lower initial effort, but Study 01 alone has many design views and at least one unqualified statement that conflicts with a saved plan. Curated, audited reuse is safer.

## Anticipated disagreements

- A reader-oriented contributor may want a larger illustrative set immediately. I would require each proposed addition to identify one concrete decision or failure that current prose and figures leave unclear, then test it at final page size.
- A tooling-focused contributor may prefer changing Typst's root and importing `studies/.../rendered/*.svg` directly. That is plausible if a pilot preserves preview portability, pins the renderer, and records every embedded asset in the build manifest. My stronger requirement is one source of truth and traceable bytes, not a specific copying mechanism.
- A study author may say existing `.puml` descriptions are authoritative. The D3 plan example shows that a diagram can drift from observation; the review must inspect the SQL, harness, and relevant report/analysis at the revision named in its caption.

## Falsification tests

1. Ask two or more readers unfamiliar with the studies to trace a lost update, the cache stale-fill race, and a refund question using prose alone and then prose plus the proposed figures. If the figures do not improve correct explanations or introduce new misconceptions, drop or redesign them.
2. Render the same figure set twice in the pinned Podman image and build the book from a clean commit. Fail if SVGs differ unexpectedly, any exported asset is stale, the book manifest omits figure hashes, or the PDF clips text. A digest mismatch would invalidate the proposed reproducibility path.
3. For every figure, have a reviewer map each entity, write, transaction boundary, acknowledgement, and negative-control branch to the named SQL/harness/report at its stated commit. Any unsupported mechanism claim forces a correction or an explicit `conceptual illustration` label.
4. Rebuild after deliberately changing one `.puml` file without regenerating its SVG. If the pipeline still produces a green, unchanged manifest, the proposed provenance gate is insufficient.
