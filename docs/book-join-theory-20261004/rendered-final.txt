How to use this book


  Two reading paths

  Learn a strategy: Theory → topic → strategy.
  Choose for a situation: Study cases → business case → tested variation.


 Part                                               What you will find
 Theory                                             The mechanism, a picture, fit/failure conditions, costs and a case
                                                    link.
 Study cases                                        The business, variations, thrive/die situations and compact mea­
                                                    sured summaries.
 Appendix                                           How to judge a result, reproduce it and inspect its full evidence
                                                    card.

Reading a thrive-or-die example
• Observed: a named comparison in the cited evidence showed this effect.
• Inferred: the mechanism suggests this boundary, but that workload was not measured.
• Not measured: there is no result to resolve the choice.
Reading a number
A badge links a summary to its full claim card. Read the workload and the limit with the number. Results come
from one shared-core host with no real network between cluster containers.

 Badge                                              Meaning
 Replicated                                         Observed across whole runs; the card still names spread and limits.
 Single run                                         Direction in one run, not a stable universal magnitude.
 Mechanism                                          An implemented mechanism; no measured rate is implied.
 Analogy                                            Transferred intuition, not evidence for the new workload.
 Gap                                                Absent coverage, a missing instrument, an unsupported schema or
                                                    unstable measurement.

  Remember

  • Learn the mechanism in Theory; check its tested boundary in the matching case.
  • A read gain may carry a write, storage or correctness cost.
  • The full evidence cards are reference material, not extra teaching chapters.

Theory explains the choice. Each topic groups strategies; each strategy shows its mechanism, fit, cost and an
experiment that could challenge the expectation.

Database schemas
Choose where facts live before choosing how quickly to retrieve them. These strategies trade read work for
storage, maintenance and coordination.

Normalized rows
STRATEGY · NORMALIZED ROWS

  Key idea

  Keep each fact in its owning row; combine rows when an answer needs several owners.

The problem
A donor belongs to a charity and has many donations. Repeating the same charity details on every donation
creates extra update paths.

Joins and filter placement
STRATEGY · JOINS AND FILTER PLACEMENT

  Key idea

  Equivalent inner-join spellings often share a plan; moving an outer-join filter can change the answer.

The problem
A customer page needs each order above 100 together with its customer. Does writing the filter before the join
reduce work?

       Equivalent SQL forms               →         Optimizer transformations           →          Chosen scan and join

                                           Figure 8: Query spelling and execution.
                                          Form: sequence · Evidence: conceptual illustration

Text equivalent. Different SQL expressions can become the same scan and join. This is a conceptual optimization path, not proof of a
particular engine plan.
How it works
• Fix the returned columns and row multiplicities.
• Write the relationship and amount predicate explicitly.
• Inspect the actual plan; SQL layout does not prescribe execution order.
A small example
Illustrative tables: customers(id, name) and orders(id, customer_id, amount). Ana (id 1) has orders 11
and 14 worth 200 each. Ben (id 2) has an order worth 80 and one with NULL amount; Cara (id 3) has none.
All six forms return (Ana, 11, 200) and (Ana, 14, 200). These are example values, not measurements.
Without ORDER BY, row order is unspecified.
1. Explicit join, WHERE filter

  SELECT c.name, o.id AS order_id, o.amount
  FROM customers c
  JOIN orders o ON o.customer_id = c.id
  WHERE o.amount > 100;


2. Filter inside ON

  SELECT c.name, o.id AS order_id, o.amount
  FROM customers c JOIN orders o
    ON o.customer_id = c.id AND o.amount > 100;


3. Filtered derived table

  SELECT c.name, o.id AS order_id, o.amount
  FROM customers c JOIN (
    SELECT id, customer_id, amount FROM orders
    WHERE amount > 100
  ) o ON o.customer_id = c.id;

4. CTE naming the filtered orders

  WITH expensive_orders AS (
    SELECT id, customer_id, amount FROM orders
    WHERE amount > 100
  )
  SELECT c.name, o.id AS order_id, o.amount
  FROM customers c
  JOIN expensive_orders o ON o.customer_id = c.id;


5. CTE naming the joined rows

  WITH customer_orders AS (
    SELECT c.name, o.id AS order_id, o.amount
    FROM customers c
    JOIN orders o ON o.customer_id = c.id
  )
  SELECT name, order_id, amount
  FROM customer_orders WHERE amount > 100;


6. Comma join, both predicates in WHERE

  SELECT c.name, o.id AS order_id, o.amount
  FROM customers c, orders o
  WHERE o.customer_id = c.id AND o.amount > 100;


Expected performance: the direct join, ON filter and comma join often converge to the same plan. Simple
derived tables and folded CTEs can converge too. A plan match is a hypothesis to test, not a guarantee of
identical end-to-end timing.
A different answer with LEFT JOIN. The first expression keeps Ben and Cara with NULL order columns.
The second drops them:
Preserve every customer

  SELECT c.name, o.id AS order_id, o.amount
  FROM customers c LEFT JOIN orders o
    ON o.customer_id = c.id AND o.amount > 100;


Keep only qualifying customer-order matches

  SELECT c.name, o.id AS order_id, o.amount
  FROM customers c LEFT JOIN orders o
    ON o.customer_id = c.id
  WHERE o.amount > 100;


Filtering the child input before LEFT JOIN is equivalent to the first form. EXISTS instead returns Ana once
when the question asks only who has a qualifying order; it cannot replace required order details.

CTE folding and materialization
STRATEGY · CTE FOLDING AND MATERIALIZATION

  Key idea

  A CTE names intermediate work; folding permits joint optimization, while materialization can reuse work and block
  predicate pushdown.

The problem
The same customer-order query can scan few qualifying rows or create a large intermediate result. Reusing
expensive work poses a different tradeoff.

          Named CTE input                 →         Fold or evaluate separately         →              Filter and reuse

                                             Figure 9: The CTE execution choice.
                                          Form: sequence · Evidence: conceptual illustration

Text equivalent. Folding combines the CTE with its parent for optimization. Materialization evaluates a separate result that consumers
can reuse. No branch is universally faster.
How it works
• Check the pinned engine’s CTE syntax and default behavior.
• Keep one-use selective access separate from repeated expensive reuse.
• Verify folding or materialization in the actual plan.
• Measure saved computation against intermediate rows, memory and spills.
A small example
 Format                                             Expected behavior on PostgreSQL 17
 WITH q AS (...)                                    A nonrecursive, side-effect-free, single-use CTE normally folds;
                                                    multiple references normally materialize.
 WITH q AS MATERIALIZED (...)                       Force separate CTE evaluation; outer predicates cannot be pushed
                                                    inside it.
 WITH q AS NOT MATERIALIZED (...)                   Permit eligible CTE folding; several references may repeat compu­
                                                    tation.

Selective one-use example: add MATERIALIZED to form 5. The amount predicate stays outside the CTE, so
it cannot reduce the joined rows inside. Add NOT MATERIALIZED to allow folding when the CTE is eligible.
Repeated-use example: several consumers need an expensive deterministic calculation over the same input.
Materialization may compute it once; folding may compute it for each consumer. Selective consumers can still
favor folding by avoiding most input rows.
These are predictions. Compare default, MATERIALIZED and NOT MATERIALIZED with identical answers
and indexes. Record unsupported syntax or different defaults on the pinned YugabyteDB engine explicitly.
Documentation: PostgreSQL 17 CTE folding and materialization. This feature predates PostgreSQL 17; engine
support is not established by a version-number guess.

 strict after acknowledgement begin(R1) > ack(W1) implies the read must not return a version older than

 rollup                       A parent aggregate maintained from its children. Where it lives in the same
                              database it is updated in the same transaction; otherwise it is published, with

 rolldown                     Parent information copied onto the child to avoid a join.
 embedding                    A child collection stored inside its parent row, as JSON or an array. In this
                              corpus that means a relational JSON column, not a native document database.

                              lock plus invariant recheck or a conditional update.

 derived state                A stored structure that answers from current facts and owes its maintainer a

                              it is valid and honoured. It is a load control, not a freshness proof.
