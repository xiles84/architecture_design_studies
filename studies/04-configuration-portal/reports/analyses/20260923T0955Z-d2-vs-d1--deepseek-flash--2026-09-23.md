# Analysis — d2 document-on-parent versus d1 — deepseek-flash

> Deliverable of the `study04-v2-remaining-designs` task, the third execution task from
> `studies/04-configuration-portal/HANDOFF-AMENDMENT-01-V2.md` (tag `study-04/v2-handoff`). One of
> the eight unbuilt designs, `d2_doc_on_parent`, was implemented and measured; the other seven are
> recorded as coverage gaps with reasons in `RESULT.md` of the task attempt. This analysis edits no
> earlier analysis.

## TL;DR

- **d2 is built and passes the correctness gate** (10 checks, `failed_cells: []`), so the
  d1 ↔ d2 pair now exists as designed.
- **The predicted tradeoff did not appear at this cardinality.** Whole-document publication is
  865.9 ops/s (d1) vs 858.8 (d2), and the metadata update `w06_update_metadata` is **1651.0 vs
  1672.7 ops/s** — the embedding was expected to make the metadata write rewrite the TOASTed
  document, and at `scale small` it does not measurably. The catalogue's predicted W6 amplification
  is therefore *not confirmed here*; it needs a larger document to test.
- **The one visible difference is the search read**: `r05_search_key` 22898 ops/s (d1) vs 14433
  (d2), 1.59x slower. It is a single-run directional difference and is not attributed.

## 1. The design and the pair

`d2_doc_on_parent` ships the same statement names as `d1_doc_row`, so the harness drives it
identically. The only structural change is that the JSON document, its guard revision, its content
hash and its byte count live as columns on `installed_product` instead of a separate
`config_document` row. That removes the join from every read and puts the document in the same tuple
as the parent's short columns — which is exactly the embedding decision, isolated against d1.

Both designs keep the document's optimistic guard (`doc_revision` vs `revision` in d1) and the audit
that checks it against the parent pointer; both passed.

## 2. Measured comparison (PostgreSQL 17.11, scale small, 3 trials per measurement)

| Operation | d1_doc_row | d2_doc_on_parent | ratio (d2/d1) |
|---|---|---|---|
| r01_effective_config | 17187 | 18953 | 1.10 |
| r02_read_key | 36317 | 47098 | 1.30 |
| r03_revision_check | 42285 | 42936 | 1.02 |
| r04_list_installations | 3117 | 3508 | 1.13 |
| r05_search_key | 22898 | 14433 | 0.63 |
| wd1_write_doc (publication) | 865.9 | 858.8 | 0.99 |
| w06_update_metadata | 1651.0 | 1672.7 | 1.01 |

**Reading.** Removing the join helps the point reads modestly (r01 +10%, r02 +30%); the publication
is unchanged, as expected — both designs rewrite the whole document. The metadata update is
unchanged, which contradicts the design's stated hypothesis at this scale. The search read is 1.59x
slower in d2; with one run and a read that scans every parent row (now a wider row), that could be
real or could be noise, and this analysis does not attribute it.

Why the amplification is absent: at `scale small` the per-product document is small and the parent
row remains far under the TOAST threshold, so an update that writes the short columns and the small
`jsonb` column costs the same as writing a short row and leaving the document row untouched. The
hypothesis is testable at the 500-entry tier and the large value regime, which this task did not run.

## 3. Correctness

Both cells: `gate.passed = true` (10 checks), `failed_cells: []`, no audit failure. The audit's
`a_document_revision_mismatches` and `a_content_hash_mismatches` checks passed for d2, so its guard
revision and content hash behave as d1's do.

## 4. Where this measurement is weak

1. **One cardinality.** The amplification the design predicts is a large-document effect; `scale
   small` does not reach it. The negative result is scoped to small.
2. **One run.** The r05 difference is single-run directional; no repeat was run.
3. **Transaction and lock shape.** d2 puts the document in the same row as `current_revision`, so
   `w_revision_bump` and the publication contend on more columns than in d1. That did not show at
   small concurrency (no contention phase was run) and is unmeasured.
4. **One engine, one host.** PostgreSQL single node; no YugabyteDB arm.

## 5. The seven designs not built

`d3_doc_sections`, `d4_doc_jsonb_path`, `h1_rows_plus_readview`, `s1_snapshot_pointer`,
`s2_append_history`, `y1_colocated`, `y2_noncolocated` are recorded as coverage gaps in the task's
`RESULT.md`, each with the harness change it needs. None is reported as a result here.
