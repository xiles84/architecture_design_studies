# Analysis — `20260921T1215Z-small` — deepseek-flash

## TL;DR

- **Take the lock, not the version check, for a contended configuration key.** `c2_pessimistic_lock`
  acknowledged 3 539 increments at 886 ops/s with zero retries; `c1_optimistic_version`
  acknowledged 2 065 at 503 ops/s with 545 retries and 10 560 conflicts. Both left the counter
  exactly at the value the client believed it had published.
- **Condition that changes it:** this is one key, one installed product, 16 writers. The optimistic
  design does not *fail* here — it converges — but it pays 1.76x for the privilege. Nothing in this
  run says how the two compare at low contention, where the optimistic design's retry never fires.
- **Do not ship `x1`'s shape.** It acknowledged 3 416 increments and left the counter at 215:
  **3 201 lost updates, 93.7 %**. It also ran at 768 ops/s — faster than neither and *not* a
  number to want.
- **A parent rollup buys the overview and charges the publication.** `r04_list_installations` runs
  at 867 ops/s on the reference and 13 197 / 13 693 on `n3` / `n4` — roughly 15x. The trigger costs
  6.9x on `w05_replace_all` (83 vs 572 ops/s, p99 42 ms vs 2.5 ms); the application-maintained
  variant keeps writes near the reference. Prefer the application rollup; a trigger buys a
  guarantee, not throughput.
- **A single document is an order of magnitude smaller** for the same logical configuration
  (98 304 B against 1 032 192 B) — but this run cannot say it reads faster, because of the next
  bullet.
- **Biggest doubt:** reads whose SQL is *identical* across the eight row designs vary by 65 %
  (for example `r03_revision_check` from 25 114 to 40 010 ops/s). No read difference in this matrix
  smaller than about 1.7x is attributable to a design, and only the ~15x rollup effect clears that
  bar comfortably.

Ten of the catalogue's eighteen designs are implemented. **`d2_doc_on_parent`, `d3_doc_sections`,

Design short names used below: `n1` row-per-key reference, `n0` without the search index, `n2` with

## Conclusions

**1. For a contended key, lock.** `c2` delivered 886 ops/s against `c1`'s 503, at equal
correctness: both wrote every acknowledged increment, and the audits reproduce the counter
exactly. The interesting quantity is not the ratio but *where the optimistic design's work goes*:
545 retries for 2 065 successes — 21 % of its attempts were restarted — and 10 560 conflicts
recorded. A version check converts contention into application-level retry traffic, and on a
single-node engine with a row lock available there is no reason to pay that. **Recommendation:
lock before update for a hot configuration key; keep the version check for updates that are
usually uncontended**, where its retry never fires and it does not hold a lock while the
application reasons.

**2. The invariant is what makes that comparison real.** `x1` is the same read-modify-write without
the guard, and it acknowledged 3 416 updates while the counter reached 215. Had the study reported
throughput without the ledger, `x1` would have looked like a perfectly ordinary member of the
field. This is the second time in this repository that a control has carried the argument
(study 02's `C1`, study 03's `K0`); it is the reason the report's TL;DR states control firing
before it states anything about speed.

**3. The rollup is a purchase with a visible price.** `n3` and `n4` both collapse `r04` from an
aggregate over the configuration rows to a column read: 867 → 13 197 and 13 693 ops/s. They differ
in what they charge. `n3`'s row trigger recomputes `count` and `content_hash` for every affected
row, so a 60-key replacement pays 60 recomputations: `w05_replace_all` falls to 83 ops/s (572 on
`n1`) and p99 rises from 2.5 ms to 42 ms; `w04_publish_batch` falls to 403 from 1 023.
`n4` recomputes once per publication inside the transaction and stays close to the reference
(841 batch, 593 replace). **Recommendation: maintain the overview with a single application
statement per publication, not with a per-row trigger.** The trigger's real advantage is that a
write path cannot forget it — that is a correctness property worth naming separately from speed,
and `x2` shows the failure mode when the application's maintenance is not atomic (its rollup audit
recorded 60 mismatches).

**4. Storage is where the document design wins outright.** `d1` stores the same logical
configuration in 98 304 B of `config_document` that `n1` stores in 1 032 192 B of `config_entry` —
10.5x, and this is a deterministic measurement, not a timing. Two effects are visible in the
number: a JSON document has no per-row tuple header, and `load_entry` (688 128 B) is excluded from
the comparison because it is staging, not design. Whether the document design also *reads* faster
is not established here: `d1`'s `r01` at 15 511 ops/s is 1.7x `n1`'s 9 148, which is exactly at the
edge of what this matrix can attribute.

**5. The index control did not do what the design brief predicted, at this size.** `n0`, which has
no index on `(key)`, was *faster* than `n1` at `r05_search_key` (22 149 against 17 335 ops/s,
1.28x — inside the noise floor, so this is not a finding) and also at `r01` and `r02`, whose SQL
does not differ at all. The honest reading is that at 3 600 configuration rows the whole table is
in cache and an extra index is pure overhead; the search index needs a much larger configuration
count before it pays. **That is a hypothesis, and this run does not test it.** The cardinality
crossover is phase E and has not been run.

## Where this measurement is weak

- **One trial per measurement; every spread in the report is zero.** Rule 8 of the methodology
  says a single trial is not a measurement. Nothing here should be quoted as a design's throughput;
  the correct reading is that these are *directions* to be confirmed by phase J.
- **The 65 % floor among identical SQL is almost certainly an ordering artefact, and I did not
  control it.** All ten cells run against one `pg-single` container in one pass, each dropping and
  recreating its schema while the previous cell's writes are still being vacuumed and its pages are
  still in shared buffers. The catalog and the buffer cache therefore differ from cell to cell, and
  the design that runs last inherits the dirtiest database. The honest consequence is that
  *within-run comparisons of reads smaller than ~1.7x are unusable*, and the run order is recorded
  in the manifest so a later analyst can test this rather than assume it.
- **`x1`'s 93.7 % loss is a property of this workload, not a law.** It is 16 writers on one key.
  At low contention an unchecked read-modify-write loses nothing and its speed is not an argument
  either — the control exists to prove the ledger works, and it did.
- **Single node only.** No network, no replication, no colocation, no equal-total-resource control.
  The environment page's hazard list applies in full: eight heterogeneous cores shared with the
  client, so absolute throughput is not a capacity figure.
- **Eight designs unbuilt, cadence and churn unmeasured, no repeated conclusion run.** These are
  coverage gaps, not null results; no conclusion above may be read as "the missing designs would
  not change this".
- **One model planned, implemented, measured, validated and analysed this study.** There has been
  no independent review by a different model or a person, and I am the same agent that wrote the
  designs being compared. Where this analysis is wrong, it is likely to be wrong in a direction
  that flatters the mechanisms I chose to build. A second analyst is invited; the digest above
  identifies exactly what they should read.

## What I would measure next

1. **Repeat this matrix with three trials and a randomised, recorded cell order**, and re-run the
   identical-SQL designs first and last to measure the ordering artefact directly instead of
   inferring it. Until that is done, no read claim smaller than 1.7x from this digest should be
   repeated.
2. **The cardinality crossover (phase E)**, which is what the index control was built for: at 1,
   10, 30, 60, 120 and 500 entries, with total entries held constant and again with total bytes
   held constant. `n0` vs `n1` at 500 is the specific comparison this run failed to make.
3. **The concurrency sweep (phase F)** across 1, 2, 4, 8, 16 and 32 writers, to find where the
   optimistic design's retry cost crosses the lock's wait cost — the 1.76x here is one point on a
   curve, not the curve.
4. **Cadence (phase G)** on a 500-product fleet, where the offered rate is the fleet's, to test
   whether the write costs measured here in isolation survive jittered and burst arrivals.
