## TL;DR

- **A venue cannot compute its own abandonment rate from any design in this study.** r06
  (holds created / confirmed / expired / abandoned in a window) is `unanswerable` in every
  design of every cell — all 14 where they exist on YugabyteDB, all 13 PostgreSQL-capable
  ones there — because releasing an expired hold clears the row: an expired hold is
  indistinguishable from a seat never held. That is the number that decides
  whether 40 minutes is the right window, and the study that exists to measure the hold
  mechanism cannot produce it.
- **On YugabyteDB the layout question is the report question.** For the 100k-seat section
  map, per-seat row designs answer at 273–695 ops/s on `yb-single` (S1 679, E2 273), the
  section document (L2) at 3.1k and the section-sharded variant (L3) at 2.2k — 4.5–11x the
  row designs, and 3.2–4.3k on the 3-node topology. The document stores are also 2.7x
  smaller on PostgreSQL (20.3 MiB for L2 against 56.0 for S1).
- **The same layouts collapse on the opposite query.** On `yb-single`, "who holds this
  seat" (r02) is 4.9k ops/s for the row designs, 1.5k for the section document and
  **26.4** for the section-sharded variant — 57x slower than the document and 185x slower
  than the row designs. "Holds expiring soon" (r01) is 408 ops/s on L3 against 3.5k
  elsewhere. Sharding a section across rows buys scans with point lookups.
- **The recency report costs 50–100x every other report, in the third study to show it.**
  r05 at 196–267 ops/s on PostgreSQL and 50–70 on YugabyteDB, against 14k–20k for section
  sales and recent confirmations in the same cells. Study 01 measured this of donors,
  study 02 of customers; study 03's box office sees the same shape.
- **E0 is the one design whose own report is qualified**: r01's answer in E0 depends on
  which clock is asked, which is the design's subject, so it is declared `partial` rather
  than measured as a number.
- **The run carries no contention evidence at all.** Phases are `verify,explain,read`; the
  three control designs (S0, E0, K0) are in the matrix with nothing to fail under, so the
  report's control line is "0 of 0 fired". The gate's 65/65 per cell is an answer check.

## Conclusions

**1. Buy a hold-history table before promising an operations dashboard.** r06 is the one
report no design can answer, and it is the report an operator actually needs: how many
holds were created, how many confirmed, how many expired, how many abandoned. The erasure
is deliberate in the designs (`w_release_expired` clears `hold_id`, `customer_id` and
`hold_expires_at`), and the same erasure makes a released hold indistinguishable from an
expired one. `REPORTS.md` §3 already names the fix — a `hold_event` table written in the
same transaction as each transition — and deliberately did not build it, because it touches
all five E/K designs' write paths and needs its own protocol and its own controlled pair.
This run prices the alternative honestly: whatever the funnel costs per hold, the status quo
costs the venue the answer entirely. The next study should be that design, not another
report.

**2. If the deployment is YugabyteDB, the layout decides the seat map; if it is
PostgreSQL, it barely does.** On PostgreSQL, the 100k-seat section map runs at 6.9k–10k
ops/s in every layout (E2 6.9k, E1/L1 10k, L2 7.2k), a spread inside the run's cautions
about small differences. On `yb-single` the same question is 679 (S1) against 3.1k (L2) and
2.2k (L3); on `yb-cluster3`, 942 against 4.3k and 2.5k. The mechanism is a scan pattern:
a section document reads one row's array per section, while a row-per-seat design reads
hundreds of thousands of rows through a secondary index across the YSQL/YSQL-RPC boundary.
PostgreSQL does the same work in a fraction of the round trips, which is exactly the kind
of difference a distributed engine amplifies. **A venue that runs per-seat rows on
YugabyteDB should expect the seat map — its hottest read — to be its slowest.**

**3. The document layouts are not free; they move the cost to point lookups.** The same
`yb-single` cell that has L2 fastest at the seat map has it slowest at "seat status lookup"
(1.5k against ~4.9k for every row design), and L3 — which shards section documents — is
57x worse than L2 at 26.4 ops/s, and 185x worse than the row designs. L3's `r01` (holds
expiring soon) is 408 ops/s against 3.5k for S1, and its "hold's seats" basket page is 2.8k
against L2's 4.1k and the row designs' ~840. The pattern is consistent: document/sharded
layouts are strong on scans of a section and weak on anything that must locate a specific
seat without knowing its section. An operations desk runs both, all day; a design choice
that multiplies one query by 57 and another by 0.02 is a service-desk decision, not a
benchmark one, and it should be stated in those terms when the layouts are recommended.

**4. The recency report is the study's real reporting cost, everywhere.** r05 runs at
196–267 ops/s on PostgreSQL (K1 196, L2 250) and 50–70 on YugabyteDB — a 50–100x gap to
every other report in the same cell, and the only report that a request path could never
serve synchronously. That this shape has now appeared in three different domains (donors in
study 01, customers in study 02, box-office purchasers in study 03) is the strongest
cross-study result in the EH-02 work: "who last transacted in this window" is expensive
whenever the schema stores transactions and asks per entity, whatever the entity is called.
It should be answered by a maintained `last_purchase_at` with an index, or by a background
job, and the studies' own protocols should stop treating it as a query.

**5. Storage follows the layout, not the report set.** The reports add no schema and no
index to any design, so the storage column is the study's own: 55.2–57.7 MiB for the row
designs, 28.1 for L1 claims, 20.3 for L2's section document. A venue choosing between a
per-seat model and a document model is choosing between 2.7x more disk and a 4.5–11x faster
seat map on the distributed engine. Both numbers are measured here for the first time in
the same run.

**6. The `partial` declaration is doing real work.** E0's r01 is marked `partial` because
"which holds expire in the next ten minutes" depends on whether the database's clock or the
application's is asked, and E0 exists to expose that difference. The report prints the
caveat instead of a number, and the machine-readable declaration comes from the design
flags, not from an opinion about the design. That is the right shape for a study whose own
v1 analysis found refusals and expiry behaviour that cannot be audited after the fact.

## Where I think the measurement is weak

- **No control fired**, and none could: the phases are `verify,explain,read` and the three
  control designs (S0, E0, K0) only fail under concurrency or lifecycle load. The clean
  audit column is therefore an answer check plus a load audit, not evidence that the
  invariants are enforced. Study 03's v1 matrix is where that evidence lives.
- **Single run, one trial per cell, 5 s per measurement, closed loop, 8 connections.** The
  report's own error bar (330 comparisons over ten designs reading identical SQL: median
  1.02x, worst 1.79x) means differences below ~1.8x are not attributable here; the L2/L3
  claims above are 5–185x, so they survive it, but nothing at the 1.1–1.5x level does.
- **YugabyteDB cells are quota-bound.** These numbers describe how each layout uses a
  throttled 2-CPU node, which is the interesting comparison, but the absolute ops/s are not
  an engine limit — study 02 established that at length.
- **The 100k-seat tiers are slow enough that client effects are possible** (r05 at 50–70
  ops/s with 8 workers does little work per second), and a single-worker repeat would
  separate database time from client time.
- **No write, hold or lifecycle phase ran**, so nothing here says what the reports cost
  while holds are actually being taken — the protocol's §6 gap, and the one an operations
  desk would care about most.
- **`r06` is unanswerable everywhere, so the funnel has no measurement at all** — the
  strongest statement in this file is a statement about the schema, not a benchmark.

## What I would measure next

1. **Build the `hold_event` design** (REPORTS.md §3's held-back work) as a controlled pair
  against S1: one append-only table written in the transition statements, r06 answered from
  it, and the hot path's cost measured in the same race the v1 matrix uses.
2. **A seat-lookup-heavy workload for the document layouts**: L2 and L3 measured with a
  request mix dominated by r02 and the basket page, at `medium` scale, to see whether the
  26 ops/s point-lookup floor is a small-table artefact.
3. **Reports during a drop**: run r01/r02 concurrently with the sell-out race at 32 and 128
   buyers, which is where a box office actually runs them.
4. **The recency report as a maintained aggregate**: add `last_purchase_at` to the S1/L1/L2
   designs and compare r05's 196–267 ops/s against the maintained column, with the write
   cost measured — the design study 01's D20/D22 pair already suggests the answer, and this
   study should confirm it in its own domain.
5. **Repeat at `medium`** so the section document's advantage is not a function of one
  catalogue size.
