# Signed analysis — cache publication and deletion

## TL;DR

All three protocols met the tested strict acknowledgement contract. The useful
selection boundary is **where coherence work lives**: version validation retains
one source query on every warmed hit; synchronous fencing and acknowledged outbox
delivery remove that query, placing work on publication. An outbox is strict here
only because acknowledgement waits for delivery. It is not an automatic way to
acknowledge quickly and defer coherence.

Soft deletion, physical deletion and a cached absence marker all resisted the
controlled old-fill schedule when durable identity and non-expiring fences were
retained. Expiring the fence allowed resurrection even with a soft-delete row.
Neither soft deletion alone nor a short-lived absence marker establishes coherence.

**Do not select a universal throughput winner from these runs.** The same
version-validated candidate's first/last read-rate ratio was **2.2446** in run 1.
The fixed-budget throughput and latency records remain useful observations, but
the unexplained position/environment drift and client throttling bound attribution.

## Mechanism, predictions and selection boundary

| Choice | Where coherence work lives | Measured boundary |
|---|---|---|
| Authoritative version check | Read hits validate source generation | Exactly 1 source statement/warmed read in every read-only trial. Useful when that source read is acceptable. Source/version maintenance remains part of the writer contract. |
| Synchronous fences | Writer fences before mutation and after commit | Exactly 0 source statements/warmed read; old publication is rejected. Coordinated writers and retained fence metadata are required. |
| Acknowledged outbox | Durable event, relay invalidation, delivery commit, acknowledgement barrier | Exactly 0 source statements/warmed read; pausing delivery blocks acknowledgement. Choose for the durable delivery workflow, not as a promise of lower strict acknowledgement latency. |

Every candidate appends the same source outbox event, even when it does not
consume it. This isolates publication coordination; it does not compare the
cheapest complete production implementation of each protocol. CAS and row locks
were crossed with all three protocols, but per-key client writer ordering removes
database same-key races. Their figures measure this ordered protocol, not the
relative scalability of optimistic and pessimistic contention handling.

## Where the measurement is weak

- The same-candidate first/last effect reached 2.2446 for read rate and 2.1156
  for write rate in run 1. Later position controls were much closer. The cause
  is unmeasured; do not silently discard the first run or identify a cause by guess.
- Client throttling reached **68.86% of accounting periods** over a whole cell.
  Service counters are also recorded. These closed-loop rates are supplied
  throughput; no client/server knee or saturation boundary was measured.
- Saved configuration is 4 CPU/2 GiB; guest observation is 8 online processors
  and about 15.36 GiB. Effective caps are PostgreSQL 1 CPU/512 MiB, Redis
  1 CPU/256 MiB, client 1 CPU/512 MiB. See `RESOURCE-NOTE.md`; an unmeasured
  cluster is not proof that the physical host lacks enough resources.
- One PostgreSQL endpoint, one Redis instance, one host, 128 keys and a small
  fixed payload. Three-node/equal-total cluster and placement contrasts remain
  gaps. Rollup, rolldown and embedding are not applicable to this keyed projection.
- No capacity/eviction pressure, long-lived key turnover, fence garbage collection,
  outbox retention cleanup, crash/replay fault or real network partition was tested.
  The 300-second value TTL did not cross during these short phases. The separate
  absence marker and deliberately expired fence have explicit shorter control TTLs.
- Optional fault-timing fields are present in JSON only when recorded. Elsewhere
  the generated report's `0.000` fields are placeholders, not measured zero-duration
  stale intervals. Stale duration was recorded for the omitted outbox barrier;
  the deletion resurrection controls establish wrongness, not its duration.
- The paused-fill test uses a deterministic snapshot–mutation–publication schedule.
  It demonstrates the forbidden interleaving, not its uncontrolled occurrence rate.
  The lost-update control is likewise a controlled read/read/write/write schedule.
- No uncoordinated-writer, cross-language, payload-size or donor-portal throughput
  claim follows. No numeric book claim was registered from this tranche.
