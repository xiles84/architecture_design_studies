# Study 01 — final analysis of the available evidence

**Author:** GPT-6, through Codex · **Date:** 2026-09-12, America/Sao_Paulo.

This is a second interpretation of the existing charity-tree experiments. It extends
[the first analysis](20260912-study01--claude-opus-5--2026-09-12.md), especially the
explanation of D2 versus D3, and records disagreements below. It does not supersede that
analysis. No new database benchmark was run for this report. Study 02 is outside its scope.

## Conclusions

**Choose the design around the questions that must be cheap.** The evidence supports
three different improvements, with different costs:

1. **Index donor lookups and chronological reads.** D2 already handles a donor's history,
   first/last dates, counts and donation-ID lookups quickly. These reads do not establish
   a need to duplicate the charity ID or embed donation arrays.
2. **For charity-scoped reads, a copied key can enable a better index.** D3's main benefit
   comes from filtering donations by charity directly, often in the required date order.
   It adds two indexes and changes the SQL as well as copying the key. The survey's
   roughly 1.55× higher read score is a summary of those uneven gains, not a general
   acceleration of every read.
3. **Store totals when repeated aggregation is expensive enough to justify maintaining
   them.** D4 makes rankings and sums dramatically cheaper. Concurrent writers then share
   parent rows, and corrections and erasure become more expensive. The number and
   concentration of active parents matter more than a single overall write rate.
4. **Embedding is a workload-specific choice.** Whole-history JSONB performed poorly for
   the broad PostgreSQL workload. Bounded donor-only reads approached the indexed design,
   and whole-donor deletion was faster. Some YugabyteDB reads also improved. These are
   useful exceptions, but they do not establish embedding as the general winner.
5. **A maintained cache must pass concurrent correctness checks.** D9 fails that condition.
   D10 repaired the observed PostgreSQL races with a small measured write penalty. D9's
   throughput is a diagnostic comparison, not a deployable recommendation.

| Workload or requirement | Starting point supported by this study | Main qualification |
|---|---|---|
| Donor history and individual donation reads | D2: normalized tables with indexes | Benchmark larger histories before assuming counts remain cheap |
| Charity feeds, charity totals and charity rankings | D3: copied key, charity indexes and matching SQL | Extra storage, index maintenance and a consistency invariant |
| Frequent totals and rankings over many donations | D4: transactionally maintained parent totals | Test the busiest parent under realistic concurrent writes |
| Bounded donor documents with frequent whole-donor erasure | Consider D6 | Cross-donor reads and individual donation edits remain important costs |
| YugabyteDB reads dominated by donor history | Evaluate D7's physical ordering | Donation-ID lookups lost throughput in the survey |
| A cached recent-history copy is specifically needed | Evaluate D10 | Its correction was tested on PostgreSQL, not established on YugabyteDB |

## What I reviewed and how to read the numbers

The principal dataset contains **10 charities, 5,000 donors and 108,081 donations**, with
skewed charity membership and up to 496 donations per donor. The engines are PostgreSQL
17.11, single node, and YugabyteDB 2025.2.6.0, one node and three nodes. Each database node
had a two-CPU quota and 3 GiB of memory; the client shared the same laptop. See the
[environment record](../../../../docs/environments/host-zenbook-ux5406sa.md).

The [survey](../20260912-small.md) has 26 result files and passed the initial 12-query
correctness gate in every cell. That gate validates the loaded data; later write audits
are separate evidence. The follow-ups cover write costs, concurrency, mixed workloads,
history length, parent count, dataset size and cache correctness. The input register at
the end identifies all 16 runs by freshly regenerated digest.

Unless explicitly marked otherwise, rates below are **PostgreSQL operations per second**.
Read figures are generally single-trial observations. Write-cost figures use the
three-trial medians from `20260913-writes-isolated`, with a fresh load for each operation.
The trials within an operation are not three independent full database rebuilds.

The **read score is the geometric mean of separately benchmarked query throughputs**.
It gives each query equal weight in proportional terms. It is neither measured application
throughput nor an estimate for an arbitrary mix of requests. Actual blended throughput
comes from the separate mixed-workload runs. The definition is implemented in
[`geomeanReads`](../../harness/report.go).

I exclude the invalid `delete` results in `20260912-trials`, invalid `delete_person`
results in `20260912-parentwrites`, and survey correction/deletion figures affected by
preceding write phases. The [invalidation](../../results/20260912-trials/INVALID.md)
[records](../../results/20260912-parentwrites/INVALID.md) explain why.

## Why D3 beats D2 on the read score

**Copying a value does not itself make a query faster. It makes a different access path
possible, and this implementation uses that opportunity.** D2 stores the charity on the
donor. D3 also stores it on each donation, adds these
[indexes](../../sql/d3_flattened_fk/indexes.sql), and rewrites the charity queries:

```sql
CREATE INDEX donation_charity_time_idx
    ON donation (charity_id, donated_at DESC);

CREATE INDEX donation_charity_amount_idx
    ON donation (charity_id) INCLUDE (amount_cents);
```

The first index combines charity filtering with date ordering. The second locates a
charity's donations and carries the amount needed for its sum. D2's indexes on donor and
date cannot directly provide that same charity-and-date access path because the charity
key is in another table.

### The largest recency gain: stop searching donations from other charities

For the latest 50 donations to one charity, D2's saved plan walks the **global** date index,
looks up donors to determine their charity, and continues until 50 donations match. D3
jumps to the requested charity's portion of its date index and reads 50 matching donations.
It still joins donors to obtain their names; the gain is not the elimination of every join.

For the captured largest-charity example:

| Actual plan work | D2 | D3 |
|---|---:|---:|
| Donation entries examined | 151 | 50 |
| Donor index lookups after memoization | 135 | 44 |
| Shared buffer hits for the query | 411 | 137 |

Sources: the saved [D2 plan](../../results/20260912-small/pg-single/plans/d2_normalized_indexed.txt)
and [D3 plan](../../results/20260912-small/pg-single/plans/d3_flattened_fk.txt), `q12`.
Buffer hits count accesses, not necessarily distinct pages or disk reads.

This is the mechanism behind the improvement: **find matching rows in the required order
and stop early**. PostgreSQL documents why an ordered index is especially useful with
[`ORDER BY` and `LIMIT`](https://www.postgresql.org/docs/17/indexes-ordering.html).

The plan snapshot does not prove the full 9.23× throughput ratio. It samples one charity;
the benchmark samples charity IDs uniformly, including much smaller charities. It is
reasonable to expect more discarded candidates for a smaller charity in D2, but the
stored plans do not quantify that effect across the whole workload.

### The largest aggregation gain: restrict the donation scan before summing

For `q08`, D2's captured plan scans all **108,081 donations** and hash-joins the donor
selection. D3's plan visits the **31,293 donations of the selected charity** through the
charity index and avoids that join. It still sums those donations; this is not a stored
total. The ranking queries similarly filter donations directly, aggregate by donor, then
fetch the names of the selected winners.

**Do not attribute the measured gain to zero table access.** Although D3's `q08` plan says
`Index Only Scan`, it also says **`Heap Fetches: 31293`**. The captured execution visited
the table for every matching donation. A covering index permits an index-only result,
but PostgreSQL may still need table visibility checks; see its
[index-only scan documentation](https://www.postgresql.org/docs/17/indexes-index-only-scans.html).
The snapshot therefore supports selective scanning and join removal. It does not prove
that the later timed phase avoided table fetches.

and [D3 JSON](../../results/20260912-small/pg-single/d3_flattened_fk.json):

| Last donor, one charity | 19,073 | 21,857 | 1.15× |

The geometric means are **5,245.48 for D2 and 8,119.85 for D3**, a ratio of **1.54797**.
The six rewritten charity queries have a combined ratio of **2.71×**. The six queries
whose SQL is unchanged have a combined ratio of **0.884×**, about 12% lower for D3.
These subset scores are calculations from the same observations, not additional trials.

**My judgment: the charity-query benefit has a credible, observed mechanism; the exact
overall multiplier remains provisional.** There is no demonstrated general speedup for
donor reads. The wider donation rows and different physical state could affect unchanged
queries, as could run-to-run noise; these data do not separate those causes.

The benefit has a price. D3's survey storage is **26.3 MiB versus D2's 18.1 MiB**, about
45% more, and it maintains five donation indexes instead of three. Its insert rate was
5,523/s versus 6,651/s, about 17% lower, but that single trial does not establish a stable
write penalty. Finally, the separate foreign keys in
[D3's schema](../../sql/d3_flattened_fk/schema.sql) ensure that the referenced donor and
charity exist; they do not enforce that the two charity IDs agree. Donor reassignment or
incorrect copied IDs require a consistency policy that this workload did not test.

## Stored totals: the strongest read gain, with the clearest contention cost

D4 replaces repeated aggregation with maintained totals and indexes on those totals.
In the survey, top-donor throughput rose from **563/s to about 34,000/s**, roughly 60×,
and the global sum rose from **286/s to about 34,000/s**, roughly 119×. The latter sums one
row per charity, so it still grows with charity count. For one charity, the sum is a
single parent lookup. See the [survey](../20260912-small.md) and
[D4 query definitions](../../sql/d4_rollup_trigger/queries.sql).

The distinction is the amount of work eliminated. Scanning thousands of donations to
rank donors is expensive; finding a donor's first and last date through an index is
already cheap at this scale. A count is mathematically an aggregate too, but here it
counts a short indexed donor history. The evidence supports maintaining **expensive
aggregates**, rather than treating every aggregate function as a reason to add a rollup.

These are the median write rates on PostgreSQL from the
[isolated write experiment](../20260913-writes-isolated.md):

| Operation | D3 indexed baseline | D4 totals | D6 whole-history JSONB | D9 cache, known incorrect |
|---|---:|---:|---:|---:|
| Add donation | 6,668 | 2,783 | 4,007 | 5,210 |
| Correct amount | 6,678 | 2,700 | 418 | 4,794 |
| Remove donation | 7,324 | 1,333 | 457 | 5,347 |
| Edit donor profile | 6,651 | 6,103 | 7,194 | 7,109 |
| Erase donor and donations | 5,595 | 389 | 7,397 | 3,771 |

D4's insert penalty is about **2.4×**, with 3% spread between its trials. Its deletion
rate has **147% spread**; D6's amount-correction and donation-deletion rates have
**155% and 172% spread**. Those cells demonstrate substantial cost, but their exact
multipliers are unstable. D4's donor erasure is about 14× slower in this implementation:
its row trigger recomputes extrema repeatedly as child donations are removed. That is
not a lower bound for every possible rollup implementation.

The contention experiments explain when the insert penalty changes:

| At 32 writers | D3 inserts/s | D4 inserts/s | D3 / D4 |
|---|---:|---:|---:|
| 10 charities | 8,475 | 951 | 8.9× |
| 1,000 charities | 8,838 | 6,154 | 1.44× |

Sources: [10-charity](../20260913-contention-10charities.md) and
[1,000-charity](../20260913-contention-1000charities.md) runs. These are single trials,
but the change is consistent with reducing competition for shared parent totals. Parent
count alone is not sufficient: skew and the rate directed at the busiest parent matter.

The benefit also survived one blended workload. At four readers and four writers, D4
handled about **13,000 reads/s**, versus D3's **3,000**, alongside roughly 1,300 and 1,100
writes/s respectively. These are actual mixed rates, not geometric scores. The change
from eight readers to four readers also changes reader concurrency, so the reported
fraction of throughput retained cannot isolate write interference by itself.
[Mixed-workload results](../20260912-mixed.md)

### Application maintenance and isolation need narrower conclusions

D5 implements application-maintained rollups for **inserts**; its correction/deletion
paths do not provide equivalent maintenance. Its faster raw correction/deletion rates
must not be used to claim cheaper correct rollups.

In the [concurrency sweep](../20260912-concurrency.md), D5's plain-update strategy was
slower than D4 throughout. However, D5's explicit lock-first strategy reached about
**1,700 inserts/s at 32 writers**, versus D4's roughly **1,100/s**. Application maintenance
was therefore not slower under every tested strategy. Optimistic version checks reached
only **534/s** there; retries consumed the attempted work.

At eight writers, D5 plain updates achieved about 2,300/s under read committed, versus
324/s with 33,388 retries and 28 terminal errors under serializable. The audited committed
rollups remained correct. This supports read committed for these atomic update statements;
it does not establish that stricter isolation is unnecessary for different business rules.

## Embedding, caching and physical locality solve different problems

### Whole-history embedding is unattractive for the broad PostgreSQL workload

D6's survey read score was **951 versus D3's 8,120**, about 8.5× lower. Its JSONB arrays
make individual donation edits expensive and make cross-donor questions traverse many
embedded records. A donor profile edit, however, did not show a comparable penalty, and
erasing the entire donor was **1.32× faster** in the three-trial write experiment.

The [history-cap experiment](../20260913-regime-history.md) reduced the maximum from
496 donations per donor to 20 while retaining approximately 108,000 donations by adding
donors. D6's amount-correction throughput rose from **434/s to 1,381/s**, but D3 still
handled **6,020/s** in the capped case. Its broad read score remained about 7.7× lower.

When reads were limited to the donor portal, D6 approached D3: approximately **23k versus
29k reads/s** with normal history, and **26k versus 29k** with capped history. These
single-trial gaps do not establish a read win. The erasure advantage is more consistent
across repeats, but each donor-erasure trial was very short; it should be rechecked over
longer sustained runs before designing around a precise 32% gain.
[Normal portal](../20260913-portal-unbounded.md), [capped portal](../20260913-portal-cap20.md)

“Embedding never wins on reads” is too broad across engines. On three-node YugabyteDB,
D6's top-donor query reached **237/s versus D3's 70/s** in the survey, a 3.4× advantage for
that specific comparison. D4 was still much faster for that question. This is an
engine-specific exception, not an overall recommendation for D6.

### A cache's throughput is secondary to whether it returns the right history

D9 maintains a donor's latest 20 donations alongside the real donation table. Concurrent
tests exposed both ordering errors and missing donations. Its insert-only audit in the
isolated write run found **10 incorrect donor caches** despite zero SQL errors; later
rebuilds can hide earlier corruption.

[D10's trigger](../../sql/d10_embedded_hybrid_locked/triggers.sql) sorts merged entries
by donation time and ID, and takes the donor lock before rebuilding the cache in a
separate statement. The supplied PostgreSQL cache-fix tests recorded no cache mismatches
for D10. The repeated comparison measured **4,650 versus 4,834 inserts/s**, **4,346 versus
4,469 corrections/s**, and **4,845 versus 4,928 deletions/s**: roughly 2–4% less throughput
than D9. Donor erasure was 11% lower, near D10's 14% trial spread.
[Race reproduction](../20260913-d9-cache-race.md), [mixed fix tests](../20260913-cache-fix.md),
[repeated fix costs](../20260913-cache-fix-writes.md)

These results support repairing the cache if one is needed. They neither prove correctness
under untested isolation levels and mutations nor demonstrate the fixed version's cost
on YugabyteDB.

### On YugabyteDB, avoiding a second storage lookup can matter

In the three-node survey, donor-history throughput was **2,041/s for D3**, **3,922/s for
D7** and **3,965/s for D9**. D7 puts donor ID and descending donation time in the primary
key, making the desired history a directly readable range.

The saved `q09` plans give a concrete explanation: for the same four-donation donor,
[D3 uses two storage read requests](../../results/20260912-small/yb-cluster3/plans/d3_flattened_fk.txt),
one index and one table request;
[D7 uses one](../../results/20260912-small/yb-cluster3/plans/d7_yb_child_colocated.txt).
That is stronger evidence than assuming every donor query contacts every cluster node.
D9 also uses one storage request in its saved plan, but that snapshot uses a different
donor and should not be treated as an identical-key plan comparison.

D7 has a tradeoff: donation-ID throughput was **2,395/s versus D3's 3,406/s**, about 30%
lower in the same survey. Evaluate the actual mix of donor and donation-ID queries before
choosing its physical layout.

## Indexes, foreign keys and database topology

**Secondary indexes earned their place even in the smallest dataset.** The tiny run had
**8,999 donations**; D2's score was **12,417 versus D1's 4,004**, about 3.1× higher. Small
tables do not make every access pattern equivalent. This is a single-trial result, and
individual queries can still favor a scan.
[Size comparison](../20260913-regime-size.md)

**Keep foreign keys unless a relevant measured cost justifies another integrity design.**
Dropping them did not establish an insert benefit on PostgreSQL or in the repeated
three-node YugabyteDB run. However, “no measurable difference in any test” overstates the
evidence. In the repeated three-node run, whole-donor erasure reached **184/s without
foreign keys versus 121/s with them**, a 1.51× gap with respective spreads of 2.2% and 3.3%.
That merits a focused follow-up. The survey's one-node YugabyteDB insert gap, **548/s
without foreign keys versus 300/s with them**, also remains unresolved by repeats on that
topology. These are operation-specific observations, not reasons to discard all constraints.
[Isolated writes](../20260913-writes-isolated.md), [survey](../20260912-small.md)

For D3, the survey measured:

| Topology | Read score | Inserts/s |
|---|---:|---:|
| PostgreSQL, one node | 8,120 | 5,523 |
| YugabyteDB, one node | 641 | 300 |
| YugabyteDB, three nodes | 644 | 156 |

PostgreSQL was much faster for this small local workload. The third row does not measure
scaling to larger-than-memory data or resilience to machine failure. All nodes shared one
host, and three database nodes received three times the aggregate database CPU quota.
The results establish what this setup delivered, not which engine should win at scale.

Replication adds coordination work. In YugabyteDB, Raft persistence requires a **majority
of tablet peers**, rather than confirmation from every replica. At replication factor
three, that is two peers. The supplied experiment did not measure failover, and the
wall-clock write penalty cannot be attributed entirely to quorum cost without further
controls. [YugabyteDB replication documentation](https://docs.yugabyte.com/stable/architecture/docdb-replication/replication/)

## Where I think the measurement is weak

- **Most read and regime results are single trials.** The regenerated survey reports
  1.04× median and **1.69× maximum** disagreement across its 36 D4/D5 control comparisons.
  These are descriptive checks, not confidence intervals or a universal significance
  threshold. They cannot validate an exact 1.55× aggregate advantage. Repeated, alternated
  D2/D3 measurements are the missing evidence.
- **One design decision can change several physical mechanisms.** D3 changes row width,
  two indexes and query shape together. The pair measures the implemented denormalization
  package, not the independent effect of copying a column. Likewise, D4 measures these
  particular totals and trigger algorithms, not all possible precomputation strategies.
- **Plans are snapshots.** The principal D2/D3 plans use the largest charity, whereas timed
  reads sample charities uniformly. Plans are captured before the read benchmark. Their
  heap-fetch counts, cached pages and plan choices need not describe every timed request.
- **The host couples client and server performance.** CPU scheduling, laptop thermals and
  background database work can affect designs differently. Equal quotas do not guarantee
  identical noise. Real networks also change the costs of distributed operations.
- **Regimes preserve approximate volume, not identical data.** The capped case has 108,089
  donations and 12,015 donors; the 1,000-charity case has 108,568 donations versus the
  base's 108,081. The volume differences are small, but more donors and different parent
  sizes change both work and contention. “Unbounded” here still means a finite generated
  history with maximum 496, not a long-running database allowed to grow indefinitely.
- **Some repeated measurements remain unstable or short.** D6 donation mutations and D4
  deletion have wide spreads. Whole-donor erasure uses only about 625 deletions per trial
  in the repeated run, giving subsecond windows for fast designs. Three close trials are
  useful evidence, but not a sustained-capacity guarantee.
- **Mixed runs change reader count as writers are added.** A throughput-retained percentage
  includes that change. The cache-fix run has no all-reader split at all: its first 4:4
  split is the displayed baseline, so “100%” there does not mean “no read degradation.”
- **Latency tails are optimistic.** The closed-loop client waits for replies; it cannot
  represent requests accumulating while the server stalls. Do not turn its p99 or maximum
  values into service guarantees.
- **Correctness coverage has boundaries.** D10 passed the recorded PostgreSQL cases. D3's
  copied-key invariant, donor reassignment, and D5's missing update/delete maintenance
  are not covered by the initial loaded-data gate. Tests of successful committed writes
  also do not erase the terminal errors observed under stricter isolation.

## What I would measure next

1. **Repeat D2 versus D3 first.** On PostgreSQL, alternate their execution order across at
   least five independently loaded trials. Report each query and the geometric score,
   with spread; test `q08` and `q12` separately for the largest and smallest charities.
   Capture plans and heap fetches under the same preparation as the timed phase.
2. **Separate the D3 mechanisms.** Add variants for copied key with D2 SQL/indexes, the
   charity/date index and recency rewrites, and the charity/amount index and sum rewrite.
   Include a plain charity index versus `INCLUDE (amount_cents)`, with consistent vacuum
   preparation, to test how much benefit actually comes from avoiding table fetches.
3. **Measure growth, not just a larger row count.** Run the `medium` scale and grow beyond
   the measured memory working set. One million donations alone need not exceed memory.
   Include longer per-donor histories and repeated insert/correct/delete cycles.
4. **Test the busiest parent.** Vary donor/charity skew and arrival rate while holding
   reader concurrency fixed. Compare D4 with D5's lock-first strategy at high contention,
   and test a simpler sum-only rollup to separate lock cost from extrema maintenance.
5. **Resolve the narrower exceptions.** Repeat YugabyteDB one-node FK inserts and three-node
   whole-donor erasure for longer windows. Test D10's concurrent correctness and cost on
   YugabyteDB before substituting it for the defective D9 measurements.
6. **Use the deployment decision as the control.** For distributed deployment, compare
   one large node with three smaller nodes at equal total resources, then add real network
   separation and failure tests. Use an open-loop client before assessing latency targets.

These are proposed follow-ups, not measurements completed for this analysis.

## Disagreements and extensions relative to the first analysis

The comparison is with analysis ID **`20260912-study01--claude-opus-5--2026-09-12`**.
I agree with its main PostgreSQL findings about indexes, expensive aggregation, parent
contention and D9's correctness failure. I qualify several conclusions:

- **D3's benefit needs its physical explanation.** “Charity copied down” omits the two
  new indexes and SQL rewrites. “Reads 1.6× faster” also conceals the geometric score and
  the absence of a gain on unchanged queries. The full decomposition appears above.
- **Covering does not establish zero heap fetches.** The saved D3 sum plan fetched 31,293
  heap tuples. Even the analysis template's illustrative zero-fetch claim must not be
  copied into a factual account of this run.
- **Embedding did win some YugabyteDB reads.** The broad PostgreSQL recommendation can
  stand while recognizing the top-donor exception. A conclusion spanning both engines
  needs that qualification.
- **Foreign keys did have an operation-specific measured cost.** The repeated three-node
  whole-donor deletion gap is too consistent to fold into “no measurable difference in
  any test.” It deserves replication and explanation.
- **D5 is not slower than D4 at every concurrency level under every strategy.** Lock-first
  D5 exceeded D4 at 32 writers. This does not repair D5's incomplete mutation coverage.
- **A three-replica write does not require all three acknowledgments.** Majority replication
  is the relevant mechanism; this laptop experiment does not isolate its whole cost.
- **Small numerical corrections matter for provenance.** The tiny dataset contains 8,999
  donations, and the regenerated control maximum is 1.69×. The first analysis's roughly
  11,000 donations and 1.56× control maximum should not be carried forward as current facts.

I did not build the original harness or run the experiments. I did read the first
analysis and the user's D2/D3 question before reviewing the artifacts, so this is an
independent interpretation, not a blinded review or an independent replication.
