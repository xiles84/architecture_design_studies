# Study 01 — conclusions

**Author:** Claude Opus 5 (AI) · **Date:** 2026-09-12 · **Status:** first analysis of these
results, not yet reviewed by a second analyst.

---

## Summary

1. **For "who donates the most" and "how much was donated", store the totals on the parent
   rows.** Keeping running totals on each charity and each donor answers those questions
   60–120× faster than adding up donations every time.
2. **For every other question, a good index is enough.** "Last donation", "last donor",
   "first and last donation of a person" and "how many donations" were already answered at
   30,000–40,000 per second with indexes. Stored totals made none of them faster.
3. **Stored totals slow writes down, and badly if many writers share a few parent rows.**
   With 10 charities and 32 concurrent writers, inserts were 9× slower than without them.
   With 1,000 smaller charities, the same test was only 1.4× slower. The deciding factor is
   how many writers compete for the same totals row.
4. **Embedding a donor's donations inside the donor row never came out ahead on reads.** Its
   best case — every read about a single donor, history capped at 20 donations — only tied
   with the normal design. Its one win was deleting a donor with all their donations, which
   was 1.3× faster.
5. **A cached copy of related rows can be silently wrong.** One design kept a copy of each
   donor's 20 latest donations and got it wrong under concurrent writes, with no error
   raised. A corrected version fixed it at no measurable cost.
6. **Keep foreign keys and indexes.** Removing foreign keys made no measurable difference to
   speed. Removing indexes made reads 3× slower even on a very small dataset.
7. **At this data size, PostgreSQL was 13–18× faster than YugabyteDB.** Going from one
   YugabyteDB node to three made writes 2–3× slower without making reads faster. The extra
   nodes buy fault tolerance, not speed, while the data fits on one machine.

## How to read the numbers

- **Unit:** operations per second on **PostgreSQL, single node**, unless a section says
  otherwise. Higher is better.
- **Reference design:** comparisons are made against **D3** (the normal indexed schema,
  described below), stated as "N× faster" or "N× slower".
- **"About the same"** — for results from a single run, a difference smaller than 1.5×. On
  this machine, two designs that do identical work measured up to 1.56× apart in a single
  run, so smaller gaps cannot be told apart from noise. The write-cost table uses 3 repeated
  runs, so there, smaller differences are reported when the repeats agreed closely, and
  "about the same" means within about 15%.

## Answers to the study's questions

| Question | Best approach | Speed | Compared with |
|---|---|---:|---|
| Who donates the most | Stored totals (D4) | 34k/s | **60× faster** than adding up donations (D3: 563/s) |
| Total donated, all charities | Stored totals (D4) | 34k/s | **119× faster** than adding up donations (D3: 286/s) |
| Total donated, one charity | Stored totals (D4) | 36k/s | 14× faster than D3's covering index (2.5k/s) |
| Information of the last donation | Index on donation date (D3) | 40k/s | Stored totals no faster (27k/s) |
| Who donated last | Index (D3) | 22k/s | About the same as stored totals (25k/s) |
| First and last donation of a person | Index on donor + date (D2/D3) | 34k/s | About the same as stored totals (37k/s) |
| How many donations a person made | Index on donor + date (D2/D3) | 38k/s | About the same as stored totals (37k/s) |
| A donor's 20 most recent donations | Index on donor + date (D3) | 32k/s | Faster than D9's cached copy (27k/s) |
| Latest 50 donations to a charity | Charity copied onto donations (D3) | 12k/s | **9× faster** than joining through the donor (D2: 1.3k/s) |

**What this shows:** only questions that *add up* many donations benefit from stored totals.
Questions that *find* particular donations — the latest, the first, a count for one donor —
are already fast with the right index. Stored totals would only add write cost there.

¹ From the survey, a single run, compared with D3 in the same run.
² D5's application code only updates the totals when a donation is added, so corrections and

³ These varied widely between the 3 repeats (D6 by 155–172%, D4 removals by 147%). The

Notes on the non-obvious entries:

- **D4 is slow to delete donors** because it stores the first and last donation date. When a
  donation is removed, those can't simply be decremented, so the trigger rescans the donor's
  remaining donations — once for every donation being deleted.
- **D6 is slow to correct or remove a donation** because the whole JSON array is rewritten
  to change one element. Two predicted problems did *not* appear: editing a donor's profile
  was not slower (7.2k/s vs 6.7k/s), and deleting a donor was **the fastest of any design**
  (7.4k/s vs D3's 5.6k/s, with both repeats agreeing within 2%), because the donations go
  with the donor row in a single delete.
- **D4 uses less storage than D3** (23 MiB vs 26 MiB): with stored totals, D3's extra index
  for charity totals is no longer needed.
- **D5 is slower than D4 at every concurrency level**, because the application makes three
  round trips for what the trigger does inside the database.

## When a normally slower design is the right choice

Each design above loses somewhere. These are the situations tested in which that weakness
disappears, and what happened.

### Stored totals, when writes are spread across many parents

**Why it's normally a problem:** every new donation updates its charity's single totals row.
With few charities, concurrent writers queue behind each other on that row.

**What was measured:** the same donations and donors, split across 1,000 charities instead
of 10.

| | 10 charities | 1,000 charities |
|---|---|---|
| Add a donation, D4 vs D3 | 2.1× slower | about the same (1.1× slower) |
| Reads, D4 vs D3 | 3.9× faster | 1.7× faster |
| 32 concurrent writers: D4 | 951/s (9× slower than D3) | 6.2k/s (1.4× slower than D3) |

With 10 charities, stored totals were still acceptable up to about **4 concurrent writers**
(1.2× slower than D3); at 8 writers they were 2.3× slower.

**Recommendation:** use stored totals when writes spread across many parent rows, or when
few writers run at once. Avoid them when many concurrent writers hit a handful of parent
rows. In that case, add up at read time with a covering index — or update the totals
asynchronously, which this study did not test.

### Embedded donations, when every read is about a single donor

**Why it's normally a problem:** any question spanning many donors (totals, rankings,
recent activity) has to open every donor's array.

**What was measured:** (a) donation history capped at 20 per donor, with the same total
number of donations, and (b) a workload of donor-portal reads only (a donor's own recent
donations, count, first and last), with no cross-donor questions.

| | Normal history | History capped at 20 |
|---|---|---|
| Donor-portal reads, D6 vs D3 | 1.3× slower | about the same (1.1× slower) |
| All 12 questions, D6 vs D3 | 9.5× slower | 7.7× slower |
| Correct an amount, D6 vs D3 | 15× slower | 4.3× slower |

Capping history made D6's writes much cheaper, but did not fix cross-donor reads: the
total number of donations to scan is unchanged.

**Recommendation:** consider embedding only if all three hold — reads are always about one
donor, each donor's history is naturally limited, and cross-donor questions are answered
somewhere else. Even then, it only matched D3 on reads. The one operation where it was
faster is deleting a donor with all their donations (1.3× faster than D3, 19× faster than
stored totals), so it suits a system where bulk erasure — for example privacy deletion
requests — is a major workload.

### A cached copy of recent donations, on a distributed database

**Why it's normally a problem:** on single-node PostgreSQL, the index already returns a
donor's recent donations faster than reading the copy (32k/s vs 27k/s), so the copy is extra
storage and write work for nothing.

**What was measured:** the same designs on a 3-node YugabyteDB cluster.

| A donor's 20 most recent donations (YugabyteDB, 3 nodes) | Speed |
|---|---|
| D3 reference (index) | 2.0k/s |
| D9 cached copy | 4.0k/s — **2× faster** |
| D7 donations stored by donor | 3.9k/s — **2× faster** |

On a distributed database, following an index to the donations can mean calls to several
nodes, so keeping them together pays.

**Recommendation:** on YugabyteDB, prefer D7 over a cached copy. It gave the same 2×, had the
fastest inserts of the three in that run (239/s vs D9 210/s and D3 156/s), and has no second
copy that can go wrong.

### Designs with no situation where they came out ahead

- **No indexes (D1):** even with only 11,000 donations, reads were 3.1× slower than with
  indexes, and inserts were no faster.
- **No foreign keys (D8):** no measurable speed difference in any test. A reason to drop
  them would have to be organisational, not performance.
- **Stored totals kept by the application (D5):** acceptable only for data that is never
  corrected or deleted, since its code only updates totals when a donation is added.

## The cache bug

D9 keeps a copy of each donor's 20 latest donations inside the donor row, maintained by a
database trigger. **Under concurrent writes it was silently wrong**: in every 30-second test
with several writers, 3 to 5 donors' copies differed from their real donations. No error was
raised.

There were two separate causes:

1. **Wrong order.** When two donations for the same donor were saved at almost the same
   moment, the copy stored them in the order the saves *finished*, not by donation date.
2. **Missing donation.** Correcting or removing a donation rebuilds the donor's copy. If
   another donation for that donor was saved while the rebuild was waiting its turn, the
   rebuild wrote a copy without it.

**D10 fixes both**: it sorts the copy by date instead of adding to the front, and locks the
donor row before rebuilding. It was correct in every test. Adding, correcting and removing
donations were within 4% of D9's speed; deleting a donor was 11% slower, close to that
test's 14% variation between repeats.

**Why the first check missed it:** the correctness check ran only once, after all write
operations — by which time later corrections and removals had rebuilt most of the damaged
copies. Checked straight after the concurrent inserts, 10 of 5,000 copies were wrong.

**Stored totals (D4, D5) were correct in every check**, under every locking strategy and
isolation level.

## Concurrency and transaction isolation

Measured on D5, where the application controls how the totals rows are locked.

- **Locking first beats check-and-retry when writers compete.** With 32 writers, locking the
  totals row first handled 1.7k inserts/s. Reading a version number and retrying when it had
  changed handled 534/s, because most attempts had to retry. With few writers the two were
  about the same.
- **Serializable isolation was 7× slower and bought nothing.** 2.3k/s under read committed
  vs 324/s under serializable, with 33,000 retries, and 28 transactions still failed. Read
  committed was already correct for these statements.
- **Reads slow down when writes run at the same time, but the ranking held.** With 4 readers
  and 4 writers, D4 kept only 45% of its read speed — the largest drop — but at 13k/s it was
  still about 4× faster than D3 (3.0k/s).

## PostgreSQL vs YugabyteDB, one node vs three

Each database node had the same CPU and memory in every setup.

- **YugabyteDB, one node, was 13× slower on reads and 18× slower on inserts than
  PostgreSQL** (D3: 641 vs 8.1k reads/s; 300 vs 5.5k inserts/s). This is the expected
  overhead of a distributed storage engine when the data fits on one machine. It says
  nothing about what YugabyteDB is built for — surviving node failures and data larger than
  one machine — neither of which was tested.
- **Going from one YugabyteDB node to three made writes slower and reads no faster.** Inserts
  were 1.9× slower for D3 and 3× slower for stored totals (D4), because every write must be
  confirmed by three nodes. Reads were about the same.

## How far to trust this

- **One laptop.** The benchmark client and the databases shared 8 CPU cores, and cluster
  "nodes" talked over the same machine, not a real network. Real clusters will show *larger*
  multi-node write penalties than these.
- **Small data.** About 108,000 donations fit in memory. The designs may rank differently
  once data no longer fits; the 1-million-donation size was not run.
- **Mostly single runs.** Apart from the write-cost table and the cache-fix test, results
  come from one run each. That is why differences under 1.5× are called "about the same".
- **Worst-case latencies are optimistic.** The load generator waited for each reply before
  sending the next request, which hides some of the slowest responses. Latency tails are only
  compared between designs, not treated as real service limits.
- **One foreign-key result is unresolved.** On single-node YugabyteDB, one run showed inserts
  1.8× slower *with* foreign keys. That wasn't rechecked there, and the repeated 3-node test
  showed no difference.
- **The test tool changed during the study.** Several measurement bugs were found and fixed
  along the way. Every run records which build produced it.
- **The mixes of questions are assumptions.** The weights for the "dashboard" and "donor
  portal" workloads are plausible guesses, not taken from a real system.
- **The author built the study.** See [About this analysis](#about-this-analysis).

## What to measure next

1. **The 1-million-donation dataset** for D2, D3, D4 and D6, to see whether the ranking holds
   when data doesn't fit in memory.
2. **Foreign keys on single-node YugabyteDB**, repeated 3 times, to settle the unresolved
   result above.
3. **Totals updated asynchronously** (for example from a queue), the untested option for
   the situation where stored totals fail.
4. **One large node vs three small ones** with the same total CPU, to separate "more
   machines" from "more CPU".
5. **A load generator that sends requests on a fixed schedule**, before treating any
   worst-case latency as a real limit.
